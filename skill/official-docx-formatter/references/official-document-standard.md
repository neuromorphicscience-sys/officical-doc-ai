# 已提供公文规范与离线执行规则

当前规则严格以命题方提供的《公文格式要求》为基础；材料未明确规定的“分类型模板差异”不自行杜撰。

| 规范项 | 当前实现 |
|---|---|
| A4 210mm × 297mm | 修改每个 `w:sectPr/w:pgSz` |
| 上 37mm、下 35mm、左 27mm、右 27mm | 修改 `w:pgMar` |
| 一般 22 行/面，原则行距 28.8 磅 | `w:docGrid` + 段落 exact 28.8pt |
| 标题二号方正小标宋_GBK，不加粗，居中 | 标题 role 的直接 OOXML 字体/字号/对齐 |
| 正文三号仿宋_GB2312 | body role 16pt 仿宋_GB2312 |
| 正文两端对齐、首行缩进 2 字符 | `w:jc=both` + `w:firstLineChars=200` + 等价 `w:firstLine=640`，兼容忽略字符缩进的渲染器 |
| 一级标题三号黑体 | heading level 1 |
| 二级标题三号楷体_GB2312 | heading level 2 |
| 三级/四级标题三号仿宋_GB2312 | heading level 3/4；“视情况加粗”暂不自动猜测 |
| 数字和字母 Times New Roman | run 中 ascii/hAnsi/cs 指定 TNR，eastAsia 保留中文字体 |
| 页码四号、`— 1 —`、奇右偶左 | 自动写入奇/偶页 footer；页数用浏览器估算触发 |
| 函首页不加页码 | 对“函”设置 first-page blank footer + titlePg |
| 附件说明正文下空一行、左空二字 | before spacing + leftChars |
| 附件另面排版，附件标识三号黑体顶格 | `pageBreakBefore` + 黑体 |
| 附件标题第三行居中 | 标题居中 + 一行前置间距近似实现 |
| 落款与正文间空两行，日期右空四字 | issuer/date role 段落间距与右缩进 |
| 附注居左空二字 | annotation role 左缩进 |

## 明确不自动改写的内容

以下属于“文字内容”而不是纯格式，默认只给建议，不自动修改：

- 为缺失标题补写“一、”“（一）”等序号
- 修改正文措辞
- 修订单位名称、日期文本、数字
- 把不规范引用括号直接替换为六角括号
- 简繁体/异体字纠正

这样可以保证默认的“内容零侵入”。

## 当前限制

1. 浏览器无法调用 Word 的真实分页器，因此是否超过 1 页采用 28 字/行、22 行/页的估算；最终分页以 Word 为准。
2. 文本框、SmartArt、OLE 嵌入对象等不做内部智能重排，尽量原样保留。
3. “标题多行应成梯形或菱形”尚未强制自动插入换行，避免错误切分词义；可在后续版本引入 AI 分词建议 + 确定性行宽算法。
4. 印章位置属于视觉对象定位，当前不自动移动印章。

## 来源与协议一致性

本参考来源于项目已验收的 `docs/rule-mapping.md` 对命题方《公文格式要求》的映射，以及 `src/lib/rules/officialRules.ts` 和 `src/lib/docx/formatter.ts`；对应软件提交 `cd1f55e29964a7f5855b2eec9f8dd72d3a03ebea`。这里未新增某学校、某文种的专属模板。机器可读规则固化在 `formatting-rules.json`，并保留原规则源码 SHA-256。

Web 使用 TypeScript 实现；Skill 使用 Python 标准库实现同一角色映射和确定性 OOXML 操作。通过相同 AST 的跨实现回归验证字体、字号、段落布局、页面、页码和正文哈希。并非把 Python 描述为可直接调用浏览器中的 TypeScript。宿主来源标记为 host-agent，inputSHA256 为额外的原文件绑定字段；其余核心 AST 字段与 Web 一致。

附件独立标题“第三行”的段前距是现有规则中的近似实现；不插入正文空白段落，也不承诺精确视觉分页。原页眉页脚部件保留，新增页码以克隆页脚承载，先去除克隆中的旧 PAGE 域，避免重复。

## 执行范围

Python 3.9+，仅标准库。输入最多 50 MB；为避免异常压缩包耗尽内存，解压总量最多 200 MB，成员最多 10,000。脚本不受模型接口的段落额度限制；宿主需根据上下文能力读取并理解全部段落，不能悄悄截断。严格 OOXML 命名空间、加密文件、数字签名文档不在本轮保证范围。含宏或签名的包拒绝修改，避免破坏签名或改变宏安全语义。

## 错误码

所有成功命令退出 0，并返回 JSON；运行失败向 stderr 返回 JSON。命令行用法错误由 argparse 返回 2。

| 退出码 | 含义 | 恢复方式 |
|---|---|---|
| 10 | 类型、空正文、损坏 ZIP、加密或输入缺失 | 从 Word 另存为有效 DOCX |
| 11 | XML、关系、Content Types 或部件路径无效 | 修复源文档后重试 |
| 12 | 文件/解压大小或成员数超限 | 拆分或压缩媒体 |
| 13 | 宏/数字签名等未支持包 | 提供不含上述特性的 DOCX 副本 |
| 20 | AST schema、角色、ID、覆盖范围无效 | 按 inspection 和 schema 修正 AST |
| 21 | 未知角色、编号冲突或低置信度待核对 | 修正结构；实际核对后才使用 reviewed |
| 30 | 输入绑定或正文/媒体完整性失败 | 重新 inspect；禁止把失败输出交付为通过 |
| 40 | 路径冲突、已存在输出、IO 错误 | 换用新的可写输出路径 |

## Skill 格式依据

按 OpenAI 官方 [Skills 文档](https://developers.openai.com/api/docs/guides/tools-skills) 组织 SKILL.md、references、scripts 与 assets；ZIP 只有一个顶层目录和一个 SKILL.md。上传接口/平台的账号权限与运行时配置不在本 ZIP 中携带。
