# 架构说明

## 核心原则

本项目把“理解”和“执行”严格拆开：

- DeepSeek：回答段落在全文中的语义角色是什么，以及层级关系是什么。
- 本地规则引擎：回答该角色应使用什么公文格式。
- OOXML 引擎：在原 DOCX 包上做确定性修改。
- 完整性校验：格式化前后提取正文字符并比较 SHA-256；不一致则阻止导出。

## 数据流

```text
DOCX（浏览器本地）
  ↓ JSZip
word/document.xml
  ↓
段落序列 + 原始样式弱特征
  ├─ 本地规则强证据（显式序号等）
  └─ Cloudflare Worker → DeepSeek
                         ↓
                    Document AST
                         ↓
公文规则映射（确定性）
  ↓
修改原 DOCX OOXML
  ↓
内容完整性校验
  ↓
规范版 DOCX（浏览器下载）
```

## AI 两阶段识别

### Pass 1：宏观结构

识别：

- 公文类型
- 标题
- 主送机关
- 附件说明
- 另页附件标识/标题
- 发文单位署名
- 成文日期
- 附注

### Pass 2：正文层级

对剩余段落识别：

- body
- heading level 1–4
- unknown

显式层次序号是强证据：

- 一级：`一、`
- 二级：`（一）`
- 三级：`1.`
- 四级：`（1）`

即使用户原文没有任何编号、字体层级或加粗信息，模型也根据连续上下文恢复层级。

## 隐私边界

DOCX 二进制、图片、嵌入对象不会发送给 Worker。Worker 只接收必要段落文本及少量弱格式特征。

未配置 Worker 或 Worker 网络不可达时，前端改用明确标注的本地演示规则；演示结果置信度较低并要求人工核对，不会标记为 DeepSeek 响应。已配置的 Worker 若返回无效 AI JSON 或配置错误，则显示错误，不会掩盖为演示成功。
